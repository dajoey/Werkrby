# P1 — Store kernel (contract)

Owner: P1 worker. Issue: helm#1. Status: spec frozen before any code was written
(work order step 1). Every rule below cites the LESSONS.md number it implements; a gate
with no lesson number does not belong in this file, and a lesson that governs the store
and is missing here is a bug in this contract.

Scope: `helm/store.py` and `tests/`. The store stays **pure**: no HTTP, no model call, no
Planka, no subprocess, no runtime coupling (PLAN decision log 2026-09-12,
"executor-agnostic product boundary"). Everything is deterministic and testable against a
throwaway SQLite file with `python3`.

## §0 Port

A prior private implementation of this store (`app/store.py`, 1,556 lines) is copied
**byte-for-byte** to `helm/store.py`. Its 158-case suite is copied to
`tests/test_store.py` with exactly two mechanical edits, both in the test file, neither
in the store:

- `from app import store` -> `from helm import store` (the package moved).
- the Windows run line in the module docstring -> `python3 tests/test_store.py`.

The port commit is the baseline: it must be green before a single gate is added, so that
every later failure is attributable to a gate and not to the port (LESSONS 31, 39).

Anything a gate later has to change inside that ported test file (fixture text a new gate
legitimately rejects, e.g. a one-character option label) is called out by name in the
commit that changes it, with the reason. Ported *assertions* are never weakened.

## §1 Park contract (LESSONS 4, 5, 6, 10)

> Every parked state carries a machine-checkable exit: a live needs-you ask, a
> `GATE: <shell cmd>` a cron can run, or a `RECHECK: <ISO date>`; parks expire <=30d;
> rechecked on the system's clock, not the owner's next app-open.

`waiting-external` is only legal when it carries **who/what** it waits on and **when we
look again**. Fields, on every door that can produce a park:

- `blocked_on` — required, >= 8 chars after strip. Rejected if it names the owner
  (`^\W*(joey|user|owner|you|me|myself|the user)\W*$`, case-insensitive). Waiting on Joey
  is `needs-you` with an ask, not a park: `waiting-external` renders as "waiting on
  someone else" with no button, so a park aimed at him waits on him invisibly, forever.
- `recheck_at` — epoch seconds or ISO-8601. Absent => default `now + 6h`
  (DEFAULT_RECHECK_S, the value the live gateway ships, so P2 migrates without a
  behaviour change). `<= now` => coerced to the default. `> now + 30d` (MAX_RECHECK_S)
  => **400**, abandonment wearing a park's clothes.
- `gate` (alias `gate_cmd`, a leading `GATE:` is stripped) — optional shell command a
  sweeper OUTSIDE the store may run to decide whether the block still holds. <= 500
  chars, single line, no NUL. Stored verbatim. **The store never executes it** (§6).

Doors:

- `post_result(state="waiting-external")` — enforced, 400 on violation.
- `put_threads` thread with `state == "waiting-external"` — enforced per-thread: the
  thread is rejected and named in `rejected[]` while the rest of the payload lands
  (partial success is a ported property and is preserved).
- `create_thread(intent="waiting")` — enforced, 400. A hand-written wait is still a wait;
  the form collects the field. Loud at creation, never silently skipped (LESSON 5).
- `snooze()` and `post_result(state="snoozed")` — **exempt**. A snooze's machine-checkable
  exit is `wake_at` plus the in-store wake sweeper (LESSON 6); demanding a second exit
  would be ceremony.

Any state other than `waiting-external` clears `blocked_on` / `recheck_at` / `gate_cmd` on
write: a stale park claim on a live thread is a card lying about its state (LESSON 10).

### Recheck sweeper (LESSONS 4, 6, 22)

- `due_rechecks(con)` — read-only. Threads with `state='waiting-external'`, `wake_at=0`,
  `0 < recheck_at <= now`, not tombstoned/suppressed. Returns `thread_id`, `blocked_on`,
  `gate_cmd`, `recheck_at`, `recheck_count`, `parked_since`.
- `apply_recheck(con, thread_id, gate_passed=None, detail="")` — the transition:
  - `gate_passed` `True` or `None` (no gate, or the gate says the block cleared): the
    thread returns to the work queue (`state='working'`, `recheck_at=0`,
    `recheck_count+1`, `dispatched_at=0`, `dispatch_attempts=0`) with an event saying
    which recheck this was and what it had been blocked on.
  - `gate_passed` `False` (the block demonstrably still holds): re-arm
    `recheck_at = now + 6h`, `recheck_count+1`, event records the gate detail. **Unless**
    the park is already >= 30d old (`parked_since`), in which case it expires into a real
    ask (below).
- `sweep_rechecks(con, run_gate=None)` — the loop. `run_gate` is an injected callable
  `(thread_id, cmd) -> (passed: bool, detail: str)`. Default `None` means no gate is run
  and everything due returns to the work queue. Injection is how the shell stays out of
  the store (§6) and how the suite drives both branches deterministically.
- **Park expiry**: a park that reaches 30 days without clearing becomes `needs-you` with a
  choice ask naming the blocker and offering keep-waiting / drop / it's-done. "Parks
  expire at 30d into a real ask" (PLAN state lattice).

## §2 Answer gate (LESSON 16)

> A question in the owner's note requires an `answers` field rendered first.

If the newest `joey-note` on the thread is newer than the newest `bot-result` (i.e. it is
unconsumed: it belongs to the round this result reports on) **and contains `?`**, then
`post_result` requires `answers`:

- a string, or a list of `{question, answer}` objects, normalised to text;
- >= 12 chars after strip (a one-word reply to a typed question is the status-word failure
  LESSON 11 exists to stop);
- otherwise **400**, quoting the question verbatim so the producer can fix its own payload
  without a second round trip.

`answers` is rendered **first** in the history event:

```
ANSWERS TO YOUR QUESTION(S):
<answers text>

[<outcome>] <note>
```

Detection is deterministic (`"?" in note`), never a model (LESSON 33). A note with a `?`
that was not really a question costs the run one sentence; a question silently ignored
costs the person the answer they asked for. The gate applies whatever state the result
carries: parking or closing a thread does not excuse leaving his question unanswered.

## §3 Self-contained gate (LESSON 17, supporting 15)

> Options must survive being screenshotted alone.

Applied to every `choice` ask at both doors (`validate_thread` for `put_threads`, and
`post_result`), across `label` and `effect`:

1. **External reference** — "as discussed/above/below/before/previously"; "see|per|refer
   to (the) above|below|attached|email|thread|ticket|card|doc|report|link|message|chat|
   screenshot|log"; "the first|second|last|previous|other one|option|choice|suggestion|
   plan|approach|version"; "option|choice <n|letter>"; "that|this|it one|thing"; "same as
   before|last time|above"; "like last time"; "do what the note|email|doc says".
2. **Deictic-only label** — the whole label is `it / that / this / them / those / these /
   same / the same / other / the other / above / below / that one / this one`.
   `Yes` / `No` are *not* rejected: the prompt is on the same card.
3. **Index-only label** — `first`, `the second`, `the last one`. A label that only counts
   through an invisible list cannot be read alone, and nothing on the card can rescue it.
4. **List-token label** — `1`, `#2`, `A`, `option 3`, `choice b`, and combinations
   (`C+D`, `A and B`, `options C & D`, `B/C`), plus a letter named inside a longer label
   or effect (`Take option B and tell them no`). Rejected **unless** the card carries the
   list itself in `ask.context` and that context *defines* every token used (§3a).
5. **Duplicate labels** in one ask (case-insensitive): two buttons that read identically
   cannot be told apart in a screenshot.
6. A `choice` ask must carry a non-empty `prompt`.

Every rejection quotes the offending label and says what to write instead.

### §3a `ask.context` — the one escape hatch

A lettered list is legible on a phone exactly when the list is **on** the phone. `ask` may
carry an optional `context` string (<= 2,000 chars, stored in `ask_context`, returned in
`ask.context`, handed to the executor in `pending_dispatch`, preserved across a snooze,
and **cleared wherever the ask is cleared** — a stale list under a different question is a
card lying about what it is asking, LESSON 10).

- A token counts as *defined* only by a definition line: `A) …`, `A. …`, `(A) …`, `A: …`,
  `A - …`, `A = …`, with a body. A letter merely mentioned in prose defines nothing.
- Only the defined tokens are licensed; `C+D` against a context that defines A and B is
  still a 400 naming `C` and `D`.
- The context is held to the same standard as the labels: if it matches the external-
  reference patterns (`A) the one we discussed above`) it is rejected, because that has
  moved the riddle rather than solved it.
- Rejections always name both fixes: write what the option DOES, or put the list in
  `ask.context`.

## §4 Bot-close rules (LESSONS 13, 18, 12, 10)

> Only Joey closes; mechanical bot-close exists only for ack-tapped threads and the
> answered-decision case (reply newer than ask, applied, nothing owed).

`post_result(state="done")` is refused unless exactly one of:

- **ack-tapped** — stored `ask_kind == 'ack'` AND a `joey-reply` exists whose body is
  literally `ack` (the tap itself). A `__redirect__` on an ack card is not an ack
  (LESSON 13).
- **answered-decision** — stored `ask_kind` in `{choice, text}` AND a `joey-reply` newer
  than the newest `bot-ask` of this generation whose body is **not** in
  `{note-only, ack, close}` (a bare close tap or a question back is not a decision), AND
  the result asserts BOTH `answer_applied: true` and `nothing_owed: true`. Both are
  explicit booleans; completion is never inferred from prose (LESSON 12).

Supporting rules:

- `post_result` records a `bot-ask` event whenever it posts a non-empty ask, because
  `ask_prompt` is a mutable column and without the event "newer than the ask" is
  unknowable one generation back (additive; no reader switches on an exhaustive kind set).
  The event carries the result's own timestamp: a synthetic offset would make a fast tap
  look older than the question it answered.
- `state='done'` may not carry a new `choice`/`text` ask: a card that asks a fresh question
  is `needs-you`, not `done`.
- **Ack in the done post** (the ever-parked case). A thread that has never carried an ask
  — parked since birth — has nothing he could have tapped, so nothing can mechanically
  close it. `state='done'` **with `ask.kind='ack'` in the same post** is therefore stored
  as `needs-you` + that ack, with a history event saying a run reported it finished and
  asked to close it; the return says `close_requested: true`, `closes_on: "his ack tap"`
  and `state: "needs-you"`, so no caller can mistake it for a close. His tap ends it
  (exception (a)). A bare `done` with no ack is still a 400, and the refusal names this
  exact fix. Nothing closes without him; nothing is left in limbo either.
- The two assertions are also **stored on the thread** (`answer_applied`, `nothing_owed`,
  rendered on the thread) and flipped off the moment either could stop being true: a new
  `joey-reply` (his answer cannot already have been applied), a result that posts a new
  `choice`/`text` ask (a new question means something is owed), a reopen.
- A result posting `done` on a thread that is **already** `done` is accepted and recorded
  as `already-closed`: a late report from an in-flight run is not a bot closing anything,
  and refusing it would make a finished run look failed.
- Generation scoping: events older than the newest `retired…` / `auto-retired…` /
  `reopened by you…` state-change are ignored, so a re-filed id cannot inherit a previous
  life's answer.
- `close_thread(actor=...)` — only a human closer (`joey`) may use the close path; any
  other actor is a 400 pointing at the two mechanical exceptions above. The default actor
  is `joey`, so the ported behaviour (and the UI's Close button) is unchanged.
- The live gateway's third exception, **silent close** of agent-opened threads Joey has
  never seen, is deliberately NOT ported. See §open-questions.

## §5 Attachments are instructions (LESSON 19, supporting 15)

> A file attached to a reply is an instruction, like a binding note (suppresses close-tap).

The store holds attachment **metadata only** — `att_id, thread_id, ts, filename, mime,
size, sha256, url, uploader, caption`. Bytes are the API's business; a store that writes
files can fail for reasons its tests cannot reach (§6).

- `add_attachment(con, thread_id, meta)` validates (filename, non-empty mime, size in
  1..25 MB, sha256 hex), dedupes per thread on `sha256`, and writes a `joey-attachment`
  event whose body names each file, its size and its URL and tells the reader to OPEN it
  before answering. History is event bodies; "attachment added" would be the status-word
  failure again (LESSON 11).
- **Unconsumed** = attachment `ts` newer than the newest `bot-result` on the thread: it
  arrived in the round nothing has acted on yet.
- `reply(con, tid, value, note="", attachments=[…])` — files may be sent **inline with the
  tap**, and are recorded before any settle predicate reads them, because a file sent with
  the tap is part of the tap.
- `reply()` with an unconsumed attachment does **not** settle, even on an `ack` tap or a
  `terminal` option: state goes to `working` and the answer dispatches carrying the files.
  The return says `settlement_suppressed: True` with the reason, lists the files, and a
  `state-change` event records that the tap did not settle it — a tap that did not do what
  the button said must never look like it did. Sending a file and settling in the same act
  is the one combination that silently throws the file away (LESSON 19; same treatment as
  a binding note, LESSON 15).
- **Every** close-tap predicate asks the same question first. There are four expressions of
  it: `reply()`'s ack branch, `reply()`'s terminal-option branch, `close_thread()` and
  `mute()` (a close tap with a rule attached — muting a card he has just sent a file to
  would drop the file and stop the card ever coming back).
- `close_thread()` / `mute()` with an unconsumed attachment are a **400** unless
  `force=True`. The tap still works when it is meant (`force`), and the refusal names the
  files and says exactly how to proceed; a silent close would discard evidence the person
  just took the trouble to send.
- `pending_dispatch` carries the thread's attachments so the executor sees them.
- The `post_result` ack-tapped exception (§4) needs no attachment check of its own: the
  suppressed tap is what queued the run, and the run reporting back is what consumes the
  files. That is the designed route — file + ack tap → dispatch carrying the files → the
  run's result closes on the ack he already gave.

## §6 Boundaries

- No HTTP, no Planka, no model call, no `subprocess`, no filesystem writes beyond the
  SQLite file itself. `GATE:` commands are DATA the store keeps and hands out; running
  them is the sweeper's (P3 dispatcher's) job, via the injected `run_gate` callable.
- No executor/runtime-specific concept in the store (PLAN 2026-09-12 decision).
- Every rejection is a `StoreError(400, detail)` whose detail is readable by the producer
  that sent the payload and specific enough for it to fix itself on retry — the ported
  file's own stated reason for hand-written validation.

## §7 Evidence (what "done" means here)

- `python3 tests/run_all.py` runs every suite (the `test_store.py` port + one suite per
  gate) and the adversarial probe; nonzero exit on any failure. Suites are **discovered,
  not listed**, so a gate that lands with a new suite cannot be forgotten here and
  silently stop running, and each runs as its own process so a crash is a reported
  failure rather than a dead harness.
- `python3 tests/probe_400s.py` fires every rejection path in §1-§5 against a throwaway DB
  in a temp dir and exits nonzero if **any** expected rejection is accepted (LESSON 40: an
  unfired guard is an untested guard). Its first section is one probe per transition rule
  in PLAN's state lattice (§open-questions 7); a refusal counts only if the thread is left
  in the state it was in before.
- Each gate lands as its own commit whose message quotes the new suite failing before the
  patch and passing after (LESSON 39).

As landed: **7 suites, 490 checks, 0 failures** — port 160, park 59, answer gate 29,
self-contained 66, bot-close 54, attachments 44, probe 78.

## §open-questions

Each is answered here with the conservative reading, and flagged for the orchestrator.

1. **Silent close (agent-opened threads Joey has never seen).** The live gateway allows a
   third bot-close exception; issue #1 names only two. Conservative choice: **not
   implemented**. A missing mechanical close costs an extra card on the list; a wrong one
   hides work. If P2 finds live producers depending on it, it comes back as its own
   contract-signed patch, not as a quiet widening of §4.
2. **Park contract at the producer's door and on hand-written waits.** The issue does not
   say which doors. Conservative choice: **all doors** (LESSON 4 says "every parked
   state"). Cost: two ported fixtures and one hand-written-card fixture in
   `tests/test_store.py` must now name what they wait on, which is a fair thing to demand
   of them.
3. **Default recheck interval.** Not specified. Chosen: 6h, matching the live gateway
   constant so P2's migration is not also a behaviour change. A missing `recheck_at`
   defaults rather than rejects (a run that named a real blocker did the honest thing); an
   out-of-range one is a 400.
4. **Question detection in a reply note.** Conservative: any `?` in the unconsumed note.
   Over-triggering costs one sentence in `answers`; under-triggering loses the question,
   which is the failure LESSON 16 was written from.
5. **"Nothing owed" is asserted, not computed.** The store cannot know whether an executor
   finished the work, so it demands two explicit booleans and records them; it never reads
   completion out of prose (LESSON 12). If a bot lies, the history still shows the original
   ask and the flags it asserted.
6. **PLAN's "8-case verification list".** The work order names one; PLAN has no list under
   that heading. Read as the **state lattice** ("every state has a machine-checkable
   exit"), whose eight transition lines are probed one by one at the top of
   `probe_400s.py`, in the order PLAN states them, plus its closing line ("a PUT may never
   resurrect done"). If the orchestrator meant a different list, the probe gains cases; it
   loses none.
7. **`mute()` is treated as a close tap** for the attachment rule (§5). It settles the
   thread AND installs a rule that stops it coming back, so muting a card he has just sent
   a file to loses both the file and the card. `force=True` is the way through, same as
   `close_thread`.
8. **A late `done` on an already-`done` thread is accepted** (`closed_by:
   "already-closed"`) rather than refused. Nothing is closed by it — the thread was
   already closed — and a 400 would make a run that finished look like one that failed.
9. **Opt-out option on every choice (LESSON 15) is not enforced here.** It is a producer /
   UI obligation, and the store cannot tell a genuine opt-out from a third real option by
   text alone; enforcing it by counting options would be theatre. Flagged for P3b, which
   derives options.
