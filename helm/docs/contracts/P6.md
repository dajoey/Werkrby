# Contract P6 — Intake routing v2 (labels as prompts)

Owner: AGY worker. Issue: helm#12. Depends: P1 store, P2 API, P3 dispatcher.
Status: spec-first contract (work order step 0). Follows LESSONS.md and PLAN.md.

The one-sentence spec: **Intake cards route through editable labels whose prompt text is data, not code.**
Intake items get classified by type of work (labels); each label maps to an editable prompt template
and an executor or webhook; a needs-human label triggers structured conversion into a well-formatted
needs-you card.

## §0 Architecture & Boundaries (LESSONS 1, 2, 33; PLAN rule 3)

1. **One Object Model**: An intake card IS a Helm thread. Labels, prompt templates, and routing targets
   are properties on or linked to the thread. Classification never spawns a detached secondary object.
2. **Prompts as Data**: Prompts are stored in the database (`labels` table), editable via API/UI.
   No hardcoded prompt changes required to tune worker instructions.
3. **Store Remains Pure**: `helm/store.py` does not invoke LLMs, webhooks, or subprocesses.
   Store gates enforce validation (label format, length, presence). Webhooks and model runs are
   dispatched by the runner / dispatcher layer (`dispatcher/`).
4. **Deterministic Facts, Judgment Off-Path**: Classifying labels and applying prompt templates is
   deterministic data mapping. LLM judgment (e.g. converting unstructured text to needs-you options)
   runs through an executor turn, never on the critical path of the store kernel.

## §1 Data Model (helm/store.py)

### 1.1 `labels` Table
```sql
CREATE TABLE IF NOT EXISTS labels (
    name TEXT PRIMARY KEY,               -- slug: lowercase, alphanumeric + dashes/underscores (3-32 chars)
    description TEXT NOT NULL DEFAULT '',-- human description for UI & classifier
    prompt_template TEXT NOT NULL,      -- the prompt brief given to the executor (min 20, max 10000 chars)
    webhook_url TEXT NOT NULL DEFAULT '',-- optional webhook target called on dispatch/completion
    executor_runtime TEXT NOT NULL DEFAULT 'hermes', -- 'hermes' | 'claude' | 'webhook' | 'none'
    convert_to_needs_human INTEGER NOT NULL DEFAULT 0, -- 1 = format output into needs-you ask
    enabled INTEGER NOT NULL DEFAULT 1,
    created_at REAL NOT NULL,
    updated_at REAL NOT NULL
);
```

### 1.2 `settings` Table
```sql
CREATE TABLE IF NOT EXISTS settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at REAL NOT NULL
);
```
Standard keys:
- `default_intake_label`: label applied when an intake card specifies no label (default: `triage`)
- `llm_conversion_enabled`: "1" or "0"
- `needs_human_prompt`: system guidance for converting raw issues to structured `needs-you` choices

### 1.3 `threads` Extension
Column `label TEXT NOT NULL DEFAULT ''` on `threads`.
Indexed via `idx_threads_label ON threads(label)`.

## §2 Store Gates & API (app/service.py + helm/store.py)

### 2.1 Label Validation Gates
- `name`: Must match `^[a-z0-9][a-z0-9_-]{1,31}$`. Reserved names like `__proto__`, `admin` rejected.
- `prompt_template`: Minimum 20 characters, maximum 10,000 characters. Must not be whitespace.
- `executor_runtime`: Must be one of `{'hermes', 'claude', 'webhook', 'none'}`.
- `webhook_url`: Empty or valid HTTP(S) URL.

### 2.2 Endpoints
- `GET /api/triage/settings` -> `{"settings": {...}, "labels": [...]}`
- `POST /api/triage/settings` -> updates settings keys
- `GET /api/triage/labels` -> list all labels
- `POST /api/triage/labels` -> create or update label
- `DELETE /api/triage/labels/{name}` -> remove label (or disable if threads reference it)
- `POST /api/triage/threads/{thread_id}/label` -> `{"label": "<name>"}`

## §3 Dispatcher Integration (dispatcher/tick.py)

1. `build_prompt` checks if `item.get("label")` exists and has an active entry in `labels`.
2. If found, the label's `prompt_template` is used as the base brief, formatting `{title}`,
   `{category}`, `{urgency}`, `{history_block}`, `{lessons_block}`.
3. If `convert_to_needs_human` is active on the label, the brief instructs the executor to produce
   a well-formed `ask` of kind `choice` or `ack` with `prompt`, `options` (self-contained, min 2),
   and `context`.
4. If `webhook_url` is configured, `dispatcher/tick.py` delivers a webhook payload on claim/completion.
