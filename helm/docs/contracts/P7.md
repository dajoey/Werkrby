# Contract P7 — Dispatcher resilience (fallback auth + note-only settle)

Owner: p7-dispatcher-fixes worker. Issue: helm#13.
Status: spec-first contract (work order step 0). PLAN standing rules 1-10 and every
LESSONS number bind. Two live-gate defects observed 2026-09-13 in the dispatcher
log (82 claims / 3 posts / 66 fails in a single afternoon; pending never drains).

## §0 The two defects, with the live evidence

**Defect A — the one-more-round SWITCH to claude can never authenticate.**
Every SWITCH-to-claude attempt since 13:26 dies with "the CLI could not
authenticate" inside the jail (log lines 2026-09-13 12:36, 12:40, 18:59, 19:24,
20:14). With zai weekly quota exhausted (HTTP 429 until 2026-09-19) there is NO
working executor: the hermes primary fails on quota, the claude fallback fails on
auth, gave_up + restore loops forever.

**Defect B — a deliberate "no action, note-only" executor conclusion re-claims
forever.** The executor rightly concludes nothing needs doing, writes a result,
the post is refused (400, answer gate) or counted posted=0, and the dispatcher
treats it as a FAIL: one note-only thread was claimed 18 times, and another
burned 6 rounds the same way. A correct judgment burns
runs and never leaves the pending queue.

## §1 Defect A — root cause (each link verified offline 2026-09-13)

1. The jailed executor's environment comes ONLY from the jail EnvironmentFile
   (`sudo systemd-run` env_reset strips the caller's env; jail.py
   `PASSTHROUGH_ENV` decides what crosses). Provider credential NAMES come from
   `HELM_PROVIDER_ENV_VARS` (jail.py `PROVIDER_ENV_VARS`).
2. The production run env (the dispatcher's run script) sets
   `HELM_PROVIDER_ENV_VARS="ZAI_API_KEY,Z_AI_API_KEY,GLM_API_KEY"` — an OVERRIDE
   that replaced the code default
   (`ZAI_API_KEY,Z_AI_API_KEY,ANTHROPIC_AUTH_TOKEN,ANTHROPIC_API_KEY`). The
   anthropic credential names were silently dropped from the fallback spawn's
   env file. **This is the missing var.**
3. The run env populates NO anthropic token at all (the ops directory has a zai
   key fetcher; no anthropic fetch exists) — so even a listed name would have
   been empty.
   This half is ops-side: the fix lands in the run script at the orchestrator's
   post-merge live gate, named in §5.
4. The other auth path, the CLI's own OAuth material on disk, is dead on this
   host and could not be refreshed under the jail anyway:
   `ProtectHome=read-only` lets the CLI READ it but never WRITE the refreshed
   token back. Bearer-token-via-env is the only jail-compatible auth path.
5. Verified against the installed claude binary (2.1.x, strings): the CLI reads
   `ANTHROPIC_AUTH_TOKEN` (→ `Authorization: Bearer <token>`) and
   `ANTHROPIC_API_KEY` (→ API-key auth), plus `CLAUDE_CODE_OAUTH_TOKEN`. It does
   NOT read `ANTHROPIC_TOKEN` (0 occurrences) — the fleet's name for the token
   must be re-exported under the name the runtime actually reads.

### The fix (in this repo)

- **jail.py**: `ANTHROPIC_AUTH_VARS = ("ANTHROPIC_AUTH_TOKEN", "ANTHROPIC_API_KEY",
  "ANTHROPIC_TOKEN", "CLAUDE_CODE_OAUTH_TOKEN")` are ALWAYS in the EnvironmentFile
  passthrough set. `HELM_PROVIDER_ENV_VARS` becomes ADDITIVE (union), never a
  replacement that can drop a fallback runtime's credentials (LESSONS 23: the
  worse condition must never wear the better-looking config; an override that
  silently disarms the fallback is exactly that).
- **tick.py**: `claude_auth_available()` — True when a bearer/api-key env var is
  present in the tick's own env (the value that will ride the EnvironmentFile),
  else the CLI's own `auth status` says loggedIn. The one-more-round switch to
  claude runs this check BEFORE claiming: unavailable → loud AUTH log, NO claim,
  NO spawn, NO extra attempt; the thread falls through to the normal gave_up →
  restore path (already loud, LESSON 9). A fallback that cannot authenticate must
  never burn a claim to find out (same reason the primary auth pre-check exists,
  contract P3 §tick-algorithm step 5).
- **stub_executor.py**: `HELM_STUB_AUTH_STATUS=logged-out` makes the stub's
  `auth status` answer `{"loggedIn": false}` so the refusal probe is real
  (LESSON 40: an unfired guard is an untested guard).

## §2 Defect B — the terminal no-action verdict (store.py gate)

**Contract change (PLAN rule 9: "contract: P7 §2" rides the commit message).**
`post_result` gains a third mechanical bot-close exception, alongside
ack-tapped and answered-decision (LESSON 18 is preserved: a bot still closes
nothing without a mechanical exception):

- The executor signals deliberate non-action with `no_action: true` — a literal
  JSON boolean assertion via `_bool_flag`, never prose (LESSON 12: completion is
  never inferred from note text). Strings/numbers 400.
- `no_action: true` is valid ONLY with `state: "done"`. A no-action verdict that
  does not settle is ambiguous and 400s.
- The close is permitted ONLY when a `joey-reply` exists that is newer than the
  current ask (this generation). His reply — INCLUDING a note-only reply, which
  is binding (LESSON 15) — is the instruction the run acted on; the verdict
  asserts the instruction required no thread action beyond recording it. No
  reply newer than the ask → 400 (nothing he said is being settled).
- The answer gate (P1 §2) is NOT exempted: his note asked a question, the
  verdict still needs `answers` (this is the live failure shape: the note-only
  results 400'd on the answer gate, and they should have — a question was asked
  and dropped).
- The note floor (80 chars) is NOT exempted (LESSON 11).
- state done + a new choice/text ask stays refused (existing rule).
- `closed_by` reports "no-action-settle" so the settle mechanism is visible in
  the API response.

**Dispatcher handling (tick.py):**

- `PROMPT_TEMPLATE` documents the verdict: when the decision genuinely requires
  no action, write result.json `{"outcome": "note-only", "state": "done",
  "no_action": true, ...}` — with `answers` whenever the note asked anything.
- `_executor_result_body` passes a literal-bool `no_action` through to the post.
  A malformed (non-bool) `no_action` is STRIPPED with a loud log line, degrading
  to the old needs-you+ack hand-back — a malformed flag must never wedge the
  thread in a 400 loop (fail toward the path with a human exit, LESSON 24).
- A posted no-action result logs `SETTLED-NOACTION` (distinct word; the log must
  distinguish "settled deliberately" from "failed", LESSON 23).
- Settle semantics come from existing post_result behavior: dispatch_attempts
  reset to 0, dispatched_at advanced past the reply → the thread leaves the
  pending queue and, being done, is never re-offered. No reclaim, retry budget
  intact for everything else.

**Preserved behavior (regression requirements):** a genuine failure still
retries with exponential backoff; gave-up at the 5-attempt cap still goes loud
and restore-to-ack still works; an executor that merely FORGOT to act (no
no_action flag) still gets the bot-close refusal.

## §open-questions

1. **Settle vs snooze.** The work order allows "SETTLES or snoozes". Chosen:
   settle (done) via the explicit assertion — a snooze hides a thread the
   executor already judged finished, and a hidden card that needed nothing is a
   deferral wearing no promise (LESSON 4's machine-checkable exit would be
   ceremony). The settle is visible in history and `closed_by`; Joey's reopen
   path (done → needs-you) is untouched.
2. **Should a note-only settle on a choice/text ask require a DECIDED reply
   (not in NON_DECISION_REPLIES)?** Chosen: NO — any reply newer than the ask
   qualifies, because LESSON 15 makes a free-text note binding, and the observed
   wedge (both note-only threads) was exactly a note-shaped instruction the executor
   rightly read as "record, don't act". The executor's explicit `no_action`
   assertion is the guard, not the reply's shape. Risk accepted: a run that
   misreads a real decision as note-only can close it — mitigated by the answer
   gate, the note floor, and the assertion being on the record (auditable in
   claims.reported).
3. **auth_precheck() in main() still only covers RUNTIME == "claude".** Chosen:
   leave it. When hermes is the primary, a dead claude sign-in must not block
   hermes work from running — the fallback's health only matters at switch time,
   which is where the new check lives.
4. **ANTHROPIC_TOKEN (fleet name) also rides the passthrough** even though the
   CLI never reads it: harmless, and it lets a future adapter read the fleet's
   own name without another jail change. The docs note (§4) is unambiguous that
   the CLI needs ANTHROPIC_AUTH_TOKEN.
5. **Found while wiring defect A: the documented auth-failure switch never
   fired.** `run_one`'s switch guard reads `out.get("ok") is False`, but the
   auth-failure return path built its dict WITHOUT an "ok" key — `None is
   False` is False, so a primary auth failure never switched despite the
   comment promising it (P3b §2.2). Fixed by setting ok/posted False on that
   path; the C3 probe drives the switch through exactly this entry point (a
   hermes auth-fail), so the repaired guard is a fired guard, not a hoped-for
   one (LESSON 40).
