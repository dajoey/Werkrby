# Dispatcher DOX

## Purpose

- Own the pump in `tick.py`: one pending thread per run, claimed before anything spawns, carried out by one runtime adapter inside an OS-level jail, with exactly one result posted back through that claim.
- Own the rails around that loop — `jail.py` (process isolation), `brake.py` (spend hold), `caps.py` (which ceiling is held by whom), `retention.py` (run-dir sweep), `skeptic.py` (the round-cap second-lane review) and `watchdog.py` (the off-host monitor).
- Keep the loop executor-agnostic: `adapters.py` holds each runtime's argv template and artifact reader, `common.py` the stdlib-only helpers. No model runs inside the pump and no caller branches on which CLI ran.
- Run headless from a timer: `tick.py --dry` reads and writes nothing, `tick.py --selftest` exercises the brake words, the adapter readers and the jail with no gateway and no billing.

## Local Contracts

- The order inside `tick.main()` is load-bearing and is what the suite probes: heartbeat (every run, including no-ops) → retention sweep → gave-up restore → spending brake → auth pre-check → round-cap check → `POST /claims` → `dispatched mode=start` → jailed spawn → adapter read → one result post. Moving a step changes what a crash costs.
- Nothing spawns before it is claimed. Every spawn path — regular attempt, skeptic review, bonus round — POSTs the claim first and expects 201; 409 means someone else holds a live claim, so skip rather than spawn. Any exit that posts no result must release the claim, or the retry 409s against its own dead lease until it expires. Posting the result back is exactly-once: retry `RESULT_POST_RETRIES` times, and treat both 202 and 409 ("already reported for this claim") as posted — a 409 read as failure double-reports.
- The single-instance `flock` fd lives in the module global `_LOCK_FD` for the life of the process and is never closed. A lock opened inside a function that returns is not a lock. A second tick logs one line and exits 0.
- `bot_rounds()` counts only run-produced rounds: `bot-result` events whose `source` is outside `NON_RUN_SOURCES` and whose `source_id` is outside `NON_RUN_RESPONDERS`. Any new dispatcher-posted note must add its responder to that set, or a thread's own hand-back permanently reads as a round past `MAX_ROUNDS` and can never be answered again.
- The brake's two reason words are distinct and load-bearing: `usage-over` means the meter was read, is fresh, and is past the line; `usage-blind` means it could not be read at all (missing, unparseable, or stale). Blind holds. Only `HELM_USAGE_BLIND_OK=1` runs blind, and the threshold compares the delta over a window, never the cumulative counter level.
- A cap the runtime does not offer must never look enforced: every entry in `CapSet.enforced_by_map()` carries a `*_enforced_by` naming its holder, including the literal "none" cases. The wall clock is the runner's, and its `timeout(1)` runs INSIDE the jail — an outer timeout kills the `systemd-run` client while the detached service keeps running, and rc 124 must mean the same thing in both jail modes. Unpriced is not free either: a runtime reporting a zero cost with a `cost_status` other than "ok" maps to `cost_usd=None` and `cost_basis="unknown/none"`, and where dollars are unreportable the token cap is the only spend signal left.
- The jail's enforcing mode is a transient systemd **service**, not a scope (scopes reject the sandbox settings). `ProtectSystem=strict` alone does not protect the home tree — `ProtectHome=read-only` is required, not optional. `ReadWritePaths` is the run dir and nothing else, and egress is `IPAddressDeny=any` plus an allowlist of resolved IPs for DNS and the configured provider hosts only. That allowlist is the COMPLETE resolved address set per host — `getaddrinfo`, IPv4 and IPv6 alike (`IPAddressAllow=` takes both), never the single A record `gethostbyname` returns: the provider hosts are CDN-fronted and rotate between lookups, and the jailed executor resolves the same name AGAIN inside the sandbox, so a one-address allowlist drops its connection at `IPAddressDeny=any` and the run reads as a provider outage — intermittent and load-dependent, not reproducible. A host that will not resolve is still skipped quietly; the set is still resolved addresses, never a wildcard domain and never general egress. It is resolved once at jail-build time, so an address first handed out mid-run is still outside it. Without systemd or passwordless sudo the mode is `fallback-degraded`, which has no filesystem scope and refuses to spawn unless `HELM_JAIL_ALLOW_DEGRADED=1`.
- `escape_probe()` must stay two-sided: it first requires a write INSIDE the run dir to land, proving the jailed command actually ran, and only then requires the outside writes to be refused. A probe that only checks "nothing appeared outside" passes vacuously when the unit dies instantly, which is why `build_service_argv` resolves a relative `argv[0]` to an absolute path or raises instead of spawning a failing unit.
- Credentials reach the executor through the 0600 env file written into the run dir, never through argv and never into a log. `sudo systemd-run` resets the caller's environment, so anything the run needs must be listed in `jail.PASSTHROUGH_ENV`; `HELM_PROVIDER_ENV_VARS` is additive only, because an override that dropped the fallback runtime's credential names killed every switched run unauthenticated. `HOME` rides through so a runtime can read its own config, which `ProtectHome=read-only` still forbids it to write.
- One `Result` shape serves every runtime, with one `from_<runtime>` reader registered in `adapters.READERS` and whatever a runtime cannot report left `None`. A new runtime is a new reader, not an `if` in the pump; `from_runtime` raises on an unknown name rather than guessing.
- Failure routing is specific: a failed last regular attempt gets ONE pass on the other runtime, and an auth failure is non-retryable but still switchable, so its return must carry `ok=False` and `gave_up_pending=True` or the switch silently never fires. A jail refusal never switches — the jail is per host, and failing closed once is the answer. Before switching to the fallback runtime, availability is checked offline, so an impossible sign-in burns no claim and no spawn.
- At the round cap the work goes to the second-lane review, never a bare hand-back. The verdict is read from the reviewer's `review-result.json`; a verdict that is absent, unparseable, unknown, or whose note is under `MIN_REVIEW_NOTE` is untrusted and falls back to the honest acknowledgement summary, which must never page. The escalation verdict grants at most one page; the needs-work verdict grants exactly one bonus round ever, marked by the literal note prefix "round-cap bonus (once per thread)" that a later review looks for before re-granting.
- Result payload gates: `no_action` rides only as a literal boolean, and a malformed flag is stripped with a loud log line and degraded to a needs-you acknowledgement so a bad flag cannot wedge the thread in a rejection loop. When the owner's note contains a question mark, the posted body must carry `answers` of at least 12 characters, shaped from the note report when the executor omitted it.
- A pending item whose sources carry `source == "learning"` is never spawned: an executor has no network and cannot write the ledger, so the tick applies the tap through the store's adoption gate and reposts the same four options on a refusal. The dispatcher also imports `helm.store` for the attempt ceiling and the title fingerprint, so those two must stay in step with the store kernel.
- `retention.sweep()` deletes only direct children of the runs root older than `HELM_RUN_RETENTION_DAYS`, never the root itself and never anything outside it; dry mode reports what it would remove without removing it. The watchdog runs on the gateway host, not this one — a monitor inside its subject's failure domain is not a monitor — pages only through a Helm needs-you thread keyed on a stable `thread_id` so repeat firings dedupe, and emits ONE page when the gateway is unreachable rather than one per missing signal.
- Every deployment coordinate is an environment variable with a loopback or empty default: `HELM_API`, `HELM_APP_TOKEN`, `HELM_RUNTIME`, `HELM_EXECUTOR_ID`, `HELM_RUNS_DIR`, `HELM_DISPATCHER_STATE`, `HELM_VM_URL`, `HELM_EXPORTER_LOG`, the `HELM_JAIL_*` knobs and the cap knobs. Name the variable; never commit a host, a path under a home directory, or a credential value here.
- `auth_precheck` spawns the executor binary `auth status` OUTSIDE the jail, so it gives the child `stdin=subprocess.DEVNULL` at both call sites. A runtime that reads stdin — the test stub does — otherwise inherits whatever the launcher had, and under anything that holds stdin open and never closes it the pre-check blocks for its whole 60-second timeout instead of about a second (measured: 20.06s to time out against a held-open FIFO, 0.09s with the stdin closed). A pre-check may never outlive the question it is asking.
- `HELM_SELFTEST_RUNS_DIR` is the one that is not a live coordinate: `--selftest` parses RECORDED run dirs — captured artifacts, never a run it made — and this points at the tree holding them. It defaults to `runs/` beside the subsystem, exactly where it read before, so unset behaviour is unchanged; a checkout with no captured runs (this one) builds a throwaway set and points this at it. `RUNS_DIR` stays separate: that is where a real run lands, and `--selftest` still builds its jail probe there.
